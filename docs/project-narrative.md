## N-001: 我为什么做这个项目

**状态**: 待补充细节  
**类型**: 动机叙事，非技术决策

### 起点

日本留学咨询是一个信息极度不对称的领域。每个学生的背景（JLPT 等级、EJU 分数、GPA、本科院校、英语成绩、目标专业）组合出一个独特的"匹配空间"，而现有的解决方案本质上都是人肉匹配——私塾老师靠经验、留学中介靠案例库、学生自己靠论坛和学长学姐的口口相传。

我做这个 Agent 不是因为"AI + 教育"是个好赛道，而是因为这个匹配问题的结构本身就适合自动化：

- **输入是结构化的**：JLPT N1/N2、EJU 分数、GPA……这些是可枚举的字段，不是模糊的"我想去好学校"。
- **知识是可检索的**：学校信息、教授方向、出愿时间、语言要求——这些是事实，不是观点。
- **输出是可验证的**：推荐的学校是否真的匹配学生的背景？学生可以自己去查证。

这个项目的定位从一开始就不是"通用 chatbot"，而是**结构化的匹配决策工具**。LLM 的角色是润滑剂，不是引擎——引擎是匹配逻辑和数据。

### 产品方向的锚点

当我在设计工具链的时候，有两条线一直没变：
1. **Agent 不能替代学生做决定**。它只能缩小搜索空间，最终的出愿选择必须是学生自己做的。
2. **私塾可以上传私有经验**。这一点决定了商业化方向——不是卖给学生，是卖给私塾，帮他们减少老师人效。

### 从代码反推的设计假设

从 `agent/prompts.py` 的 `PLANNER_PROMPT` 和 `user/profile_manager.py` 的 `UserProfile` 字段来看，产品假设是：

1. **用户知道自己想要什么专业**（`target_major` 是必填倾向的字段）
2. **用户有可量化的学术背景**（JLPT 等级、EJU 分数、GPA 都是数值/枚举）

从代码演进的时间线可以反推一些节点：

1. **意图分类的裂缝**（`PLANNER_PROMPT` 阶段）
   - 设计了 4 个标签：`[ANSWER]` / `[UPDATE_PLAN]` / `[MISSING_INFO]` / `[REPORT]`
   - 但实际业务只有两类需求：查学校信息、做匹配规划
   - 4 个标签的划分不是因为业务需要，而是因为"LLM 需要被引导"——这本身就是设计气味

2. **速度问题的暴露**（缓存层的出现）
   - RAG 检索 91 秒的记录出现在 `问题.md` 里
   - 为了解决速度问题，加了两层缓存（决策缓存 + 工具缓存）
   - 但缓存是在治疗症状，不是根因。真正的根因是：**确定性业务流程不需要 Agent 在中间"思考"**

3. **架构分析报告的诊断**（`[20260303]ARCHITECTURE_ANALYSIS`）
   - 2026 年 3 月的架构分析明确指出了演进方向：ReAct → Tool Router → 结构化匹配引擎
   - 这意味着至少在 3 月之前，ReAct 的问题已经被充分认识到了

### 教训

**ReAct 适合开放式任务，不适合确定性业务流程。** 日本升学咨询的操作步骤是已知的（匹配条件 → 查学校信息 → 给出规划），不需要 Agent 在中间做工具选择决策。

**判断框架**：先问"这个问题是检索问题还是推理问题"。检索问题用 RAG，推理问题才考虑 Agent。大多数 B2B SaaS 的"AI 功能"其实是检索问题套了 Agent 的壳。

## N-004: 这个项目教会我的

### 技术选型的判断框架（来自 ADR-007，补全）

1. 先想清楚"这个问题是检索问题还是推理问题"
2. 如果是检索问题，RAG 够用，不要上 Agent
3. 如果上了 Agent，先问："用户真的需要 Agent 做这个决策吗？"
4. **缓存是弹药不是盔甲**——先有瓶颈再加缓存，不要提前设计
5. **用户的字段需求决定了数据结构，数据结构决定了架构**——在写任何代码之前，先去问用户要什么

### 如果重来（完整版）

- 先做匹配引擎（确定性逻辑），再考虑哪里需要 LLM
- 先确认学校数据来源，再设计 RAG 结构
- 先做单轮工具调用，再考虑是否需要多轮 ReAct
- **先跟 5 个真实用户聊完，再写第一行代码**
- **先定义"什么叫一次成功的匹配"，再设计评测指标**
